01 / Problem framing

原有数据看得到金额，
却看不到“谁买了什么”。

线下交易可以留下订单和客单价，却难以持续识别消费者本人、购买品牌、品类、价格带和购物组合。会员运营、品牌协同与复购触达因此缺少可靠依据。

原来的状态

交易结束即结束。即使有销售数据，也难形成以顾客为单位、可反复使用的消费信号。

要建立的状态

把会员 ID 和购物凭证关联起来，沉淀品牌、品类、金额与时间，让下一次运营能够基于事实而不是猜测。

02 / Decision

为什么选择小票上传，
而不是先做 POS 对接？

这里的判断不是追求最复杂的技术方案，而是在系统割裂、现场执行与验证速度之间，选择一个可落地、可衡量的入口。

Choice made

先让顾客自主提交真实购买凭证，验证闭环。

直接连接 POS 或既有会员系统是长期方向，但会涉及多个系统、部门和供应商。首期以顾客上传小票为入口，先验证数据质量、权益激励与运营机制是否成立，再为后续连接留出空间。

没有优先采用的路径

POS 直连的协调与改造周期长；店员手工登记会增加现场负担且难复制；只有注册或问卷，只能得到自述信息，无法确认真实购买。

采用的路径

将会员 ID、小票图片、OCR、审核、积分和礼券组成一个闭环。以更低的接入门槛获取真实交易证据，并为未来的 POS、EC、会员系统连接保留接口边界。

顾客操作只是开始；后台审核、异常处理、权益发放和分析回流，才决定系统是否能被日常使用。

04 / Technical governance

不写代码，也要参与
技术架构与交付判断。

软件开发由外部供应商完成；我的工作是把业务和运营需求转化为验收标准、功能边界和技术判断，并参与方案、成本、范围和优先级的取舍。

顾客端：注册 / 小票上传 / 权益查询
运营端：审核 / 会员查询 / 活动 / 核销
业务服务：OCR / 积分 / 礼券 / 数据输出
运行基础：API / 数据库 / 缓存 / 图片存储 / 容器化服务

我参与的关键判断

  • 顾客端与运营后台分层，保证日常运营能独立执行
  • 不只看 OCR “能不能读”，而是看金额、税额、明细和异常怎么处理
  • 识别结果必须经过金额核验和人工兜底，不能直接触发权益
  • 在第一期控制投入，同时预留 POS、EC 和更深数据连接的扩展路径

质量标准

以金额、税额、明细、时间等业务字段的可用性作为验收维度，并要求异常可追溯。

供应商管理

比较的不只是功能清单，还包括可运维性、后续扩展、报价、实施节奏和责任边界。

数据要求

要求系统可追踪图片、识别状态、购买时点、金额、明细、积分、审核状态及异常标记。
