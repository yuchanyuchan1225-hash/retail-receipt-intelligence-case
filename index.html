01 / Business problem

金額は見える。
しかし「誰が、何を買ったか」は見えない。

既存の取引情報だけでは、訪日顧客の ID、購入ブランド、カテゴリ、価格帯、買い合わせを継続的に捉えられない。会員施策、ブランド協業、リピート提案が、推測に留まる構造だった。

従来の状態

一回限りの店舗取引。取引金額はあっても、顧客別・ブランド別に再利用できる購買シグナルが不足していた。

目指した状態

会員 ID と購買証憑を結び、ブランド・カテゴリ・金額・時点を構造化。次の運用判断に使える顧客理解をつくる。

02 / Decision rationale

なぜ POS 連携を待たず、
レシート起点にしたのか。

結論は「最も高度な技術」ではなく、「最も早く、実購買データと運用可能性を同時に検証できる入口」を選ぶことだった。

Choice made

顧客自身のレシート登録で、価値を先に実証する。

POS・会員基盤の直接連携は将来像として有効だが、複数システム、部門、ベンダーをまたぐ。初期は顧客の自発的な登録を入口とし、データ品質、特典運用、行動変化を小さく検証した。

優先しなかった選択肢

POS 直接連携は時間と調整コストが大きい。店員の手入力は現場負荷と再現性に課題がある。登録やアンケートだけでは、実際の購買内容を確認できない。

選んだ設計

会員 ID、レシート画像、OCR、審査、ポイント、ギフトを一つの運用ループにする。将来の POS・EC 連携を阻害しない、段階的な構成とした。

自動化だけを前提にせず、重複・金額異常・読み取り不確実な証憑を扱う確認導線を残した。運用不能な自動化を避けるための設計である。

04 / Technical governance

コードを書かなくても、
技術判断には参加する。

ソフトウェア実装は外部ベンダーが担当。私は事業・運用要件を、受入条件と設計判断に変換し、構成、品質、費用、実装範囲の意思決定に関与した。

顧客導線：会員登録 / レシート登録 / 特典確認
運用導線：審査 / 会員検索 / キャンペーン / 引換
業務サービス：OCR / ポイント / ギフト / 分析出力
基盤：API / データベース / キャッシュ / 画像保管 / コンテナ運用

判断したポイント

  • 顧客画面と運用画面を分離し、日常業務を成立させる
  • OCR を「読み取り率」ではなく、合計・税額・明細・例外処理で評価する
  • OCR 結果を直接の特典付与に使わず、照合と人手確認を残す
  • 将来の POS・EC 接続を阻害しないデータ・モジュール境界にする

品質基準

合計金額・税額・明細・日時など、運用上必要な項目を比較し、金額整合性と例外処理を受入条件にした。

ベンダー判断

機能の有無だけでなく、運用負荷、将来拡張、費用、実装優先順位を比較してスコープを決めた。

データ設計

画像、OCR 状態、購買時点、金額、明細、ポイント、審査状態、異常フラグを追える形に要求を定義した。

05 / My ownership

事業側
プロジェクトオーナー

課題を定義し、実現可能な入口を選び、外部開発を事業成果につなげるところまでを担った。

  • ベンダー選定、提案・見積の比較、仕様優先順位の決定
  • 会員、証憑、審査、ポイント、ギフトの業務ルール設計
  • 社内外の調整、開発・テスト・ローンチの推進
  • 初期キャンペーンとデータ検証を通じた運用モデルの確認
  • Phase 2 の会員セグメント・EC 連携・分析拡張の構想
06 / What changed

「売上集計」を、
顧客理解の起点に変えた。

実証で確認したこと

顧客 ID と購買証憑を結び、実購買の構造を継続して扱える入口を作った。購買規模、ブランド別構成、カテゴリ、価格帯、買い合わせを次の分析対象にできる状態になった。

次の段階

会員セグメント別の特典、年間累計、EC 誘導、ブランド別の顧客理解、より深いデータ連携へ拡張する。これらは次フェーズの計画であり、実証済みの機能とは区別している。
